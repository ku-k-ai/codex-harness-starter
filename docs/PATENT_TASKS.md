# 特許業務でTASKを埋めるときの例

以下は記入例であり、実案件の合格条件ではありません。基準値・対象データ・実行コマンドは、その案件で確定してください。

## 検索式の自動提案

| 項目 | 記入すること |
| --- | --- |
| 目的 | 何の技術を、どの検索システムとデータ範囲から見つけたいか |
| 固定条件 | 検索対象の時点、対象国、データベース、必須技術要素、変更不可の条件 |
| 既知の重要文献 | 必ず拾いたい文献のリスト。調整用と最終確認用を分ける |
| 品質 | 既知文献の回収、確認対象件数、検索式の実行可能性、意図との対応 |
| 費用・時間 | 生成・検索の時間、API使用量の記録方法と許容範囲 |
| 検証コマンド | 同じ入力に対して変更前後を比較し、結果を出力する既存コマンド |
| 人による確認 | 未知の重要文献の漏れ、検索意図の解釈、式の修正しやすさ |

既知文献を全件拾っても、真の再現率100%とは呼ばない。件数を減らすために必須の文献を落としたり、評価対象を変更したりしない。

停滞時の問い：入力に必要な技術要素が欠けていないか、検索語の表現と分類の組合せが適切か、件数の変化が検索範囲の違いによるものではないか。

## 一次スクリーニング・担当候補の分類

目的が「検討余地のあるものを残す」であれば、単純な正解率だけで採否を決めない。

1. 本来残すべき案件の誤除外をどこまで許すかを明示する。
2. 既知の重大な誤分類を回帰セットにする。
3. 調整に使っていない事例でも候補の品質を確認する。
4. 品質の条件を満たした範囲で時間・費用を比較する。

分類ルールや担当範囲は、依頼元の固定条件として明記する。入力の組立て・証拠の渡し方・処理順序等を改善しても、正解定義を勝手に広げない。

停滞時の問い：判定に必要な本文根拠が欠落していないか、工程や対象物の情報が混線していないか、誤りが候補生成・根拠抽出・最終判断のどこで生じたか。

## 実装前に必要な区別

- **開発の評価**：Codexの変更が、固定した受入条件を満たすか。
- **分類器や検索器の評価**：その変更によって、未知の案件の品質まで改善したといえるか。

前者の成功だけで後者を断定しない。自動確認できない条件はTASKへ残し、確認していないものを完了済みにしない。
