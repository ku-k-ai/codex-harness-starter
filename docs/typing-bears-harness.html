人が触ったのは朝の1回だけ。
8時間を回したハーネスの中身

ハーネスとは、AIに作業をさせるために周りに用意した仕組み全体のことです。優勝した人は約3か月かけてこれを作り、当日は競技エージェント（Claude Code）を起動したあと、一度も指示を入力しませんでした。面白いのは、作り込んだ仕組みを本番の1か月前に一度ほぼ全部捨て、素に近いClaude Codeに少しずつ足し直したものが勝ったことです。

3. 準備の3か月

作り込んで、捨てて、薄く足し直した

準備の前半は、人の上手なやり方をAIに教え込む方向で、仕組みをどんどん厚くしていきました。ところが9月末、ほぼ何もない素の状態で試すと、そちらの方が点が高かった。そこで一度ほぼ全部を捨て、効くものだけを少しずつ足し直したのが本番の形です。

仕組みの作り込み（イメージ）
  1. 7月下旬〜8月初め 素のまま試す 過去問（ISUCON14）を、ほぼ何も教えずに解かせた。何も言わなくても、ある程度まで自分で進めた。
  2. 8月 人のやり方を教え込む 「初期・探索・収束・最終盤」の4段階を決め、段階ごとの作業とスクリプトのひな型を用意。本人いわく、これは判断ミスだった。
  3. 8月中旬〜9月 さらに作り込む 仮説を裏付けの観測とセットで全部書き出し、大胆なものから試す二重ループのスキル。2つのエージェントを並べて走らせ、良い方を採りつつ、もう一方の手も取り込む。
  4. 捨てた
    9月末 全部消して試す 家族旅行中に実験だけ回していたら、ほぼ素の状態の方が点が高いと分かった。「新しいモデルが出たら、仕組みを一度全部消して試す」をやっていなかったと気づく。
  5. 10月初めから約2週間 薄く足し直す ほぼ何もない状態を土台に、効くものだけを少しずつ足した。止まりかけたら声をかけるhookもその1つ。これが本番の形。

役割分担をやめて、1つのセッションに

作り込んだ版では、段階ごとにサブエージェントへ仕事を任せていました。でもサブエージェントは毎回まっさらな状態から始まるので、マニュアルを読み直し、再起動の確認をやり直すことになる。最近は会話の圧縮がうまくなり、全部を1つの会話に詰め込んでも困らなかったので、1つのセッションに戻しました。

モデルが変われば、正解の厚みも変わる

本人の推測では、1年前のモデルなら作り込んだ版の方が勝っていたかもしれない（検証はしていない）。今のモデルは、ゴールと条件をきちんと伝えれば働いてくれる。だから、新しいモデルが出るたびに薄い状態から測り直す価値があります。

捨てる前も後も、やっていたことは同じです。練習問題を解かせては結果を見比べ、仕組みを直す。普通の開発でテストを回しながら製品を直すのと同じことを、ハーネスに対してやっています。

  • 判明評価用の問題は7問。過去問5問（ISUCON14・13・12と、第10回・第8回の本選。音声からの聞き取り）、今年4月ごろ公開された合同演習の問題、自作の問題1問
  • 判明変更のたびに全問を解き直すとお金がかかるので、どの問題で試すかは人が選んだ。直した内容が特定の問題にだけ効く形になっていないか、ほかの問題を悪くしていないかも確かめた
  • 判明毎回の結果を見比べ、「前は思いついて効いたのに、今回は思いつかなかった手」を拾って足した。改善点はハーネスのリポジトリにissueとして積んだ（準備のあいだは人が関わる）
  • 判明点の推移と会話の量（AIが1回に読む量）を、練習のたびにグラフで見ていた
  • 判明古い過去問は今のAIには小さすぎて解き切ってしまい、ベンチマーカー側のCPUが先に詰まる。点のばらつきも大きかった
  • 判明途中で、用意したサーバーを渡す形から、エージェントがCloudFormationで自分で立てる形に変えた。そのせいで、それ以前の結果とは比べられなくなった
  • 非公開issueの中身。どの失敗から、どの文言や部品が生まれたか

過去問の答えを、AIが覚えていないか確かめる

モデルは学習データで過去問の解説を読んでいる可能性があります。そこで、検索を使わせずに「この問題の解き方について知っていることは？」と聞いて確かめたところ、ISUCON14は典型的な解き方まで知っていました。過去問だけで測ると、仕組みの力ではなく暗記の力を測ってしまう。だから自作の問題を作りました。

自作の問題は、裏で仮想のLLM APIを呼ぶECサイトのチャットボット。商品情報と在庫をプロンプトに入れるので、在庫が変わるたびにプロンプトキャッシュが効かなくなります。在庫の更新をあえて遅らせる（lazyにする）のが解き方でした。一方、データ量を2倍にしてもほぼ差がつかず、本番の地域間の遅延のような仕掛けは思いつかなかったそうです。

4. 考え方

人がやっていた仕事を、仕組みに置き換えた

他の上位チームでは、人が競技中に口を出して方向を直していました。1位はその一言一言を、条件で動く部品に置き換えています。

人がやっていたこと置き換えた部品普段の仕事でやるなら
「この条件でやって」と伝えるCONDITIONS.md毎回変わる条件と終わりの条件は依頼文に、いつも同じ進め方は CLAUDE.md に分けて書く
始まってから準備不足に気づく事前チェックのスクリプト鍵・権限・残り枠など「ないと止まるもの」を、AIに渡す前にスクリプトで確かめる
AIに呼ばれて操作を手伝うログイン済みブラウザ・AWS・サーバーを最初から渡すテスト・ビルド・確認のコマンドと必要な権限を最初から渡し、AIが人を呼ぶ理由をなくす
「止まってないで、続けて」と言う続けさせるhook（残り時間つき）Claude Code の Stop hook か /goal で、終わりの条件を満たすまで続けさせる。締め切りの時刻も最初に伝えておく
「様子どう？」と見に行く15分ごとの見守り定期的に進み具合を要約させ、通知だけ受け取る。見守り役には作業そのものを触らせない
本当に困ったときに助けるSlack通知と外からの再起動「どうしても無理なときだけ、ここに連絡」という出口を1つだけ用意しておく
「伸びてないぞ、見直して」と言う30分停滞のhook ＋ 監査役「30分進まなかったら、それまでの案を捨てて別案を3つ出す」と書く。チェックリストを渡した別のチャットにレビューさせる
「そろそろ仕上げよう」と言う17:20の終盤hook「締め切りの○分前になったら新しいことはやめ、確認と仕上げだけにする」と書く
「どこで止める？」と迷う期待値で止める判定の道具「テストが全部通り、計測で5%以上良くなったら採用」のように、数字で決める
仕組みが合っているか試す練習問題で100回以上過去にやった似た作業を3〜5個取っておき、CLAUDE.md を大きく変えたらそれで試して比べる。AIが答えを知っていそうな題材は避ける
新しいモデルに合わせ直す9月末に一度全部消して測り直したモデルが変わったら、CLAUDE.md や手順書を外した素の状態と比べ、効いている部分だけ残す

5. 準備編を待っている部分

まだ分からないこと

準備編が公開されたら、この部分と図の点線を更新します。ポッドキャストで分かったものは、緑の枠に移しました。

  • 進め方の指示の全文素に近い形から足し直したことと、競技時間を伝えたことまでは判明
  • Stop hook の文面時間帯ごとに書き分けたことは判明。何と声をかけたかは不明
  • 監査役のチェックリストの全項目判明しているのは「固定の遅延とレート調整を両方比べたか」の1項目だけ
  • 30分停滞・17:20のhookと Stop hook の関係同じ仕組みの一部か、別の仕組みか
  • 100回の練習で何をどう直したかissueに積んだことは判明。どの失敗から何を足したかは不明
  • 自作問題とベンチマーカーの作り方チャットボットの題材までは判明
  • 8時間動かし続ける工夫止まりかけたら残り時間を添えて「続けて」と言う Stop hook（図の1に追加）
  • herdr の最終構成起動役・事前チェック・競技エージェントの3つの枠と、15分ごとの見守り（図の1に追加）
  • 練習環境と評価のしかた過去問5問＋合同演習＋自作1問。暗記の確認もした（図の3に追加）
